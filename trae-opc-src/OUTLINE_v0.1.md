## 01 / 一个信念（5 分钟）

### P4 提示词是反人类的 · 2 分钟
- **屏幕上：** 左右对比。左：一条真实的长提示词（从案例库里挑一条几百字的英文提示词，密密麻麻）。右：一个餐饮老板真实会说的话，比如"帮我做张中秋海报，放我们家招牌菜"。中间一行大字：**提示词是反人类的**。
- **素材：** 案例库里挑一条长提示词（我来挑）
- **讲稿：** 这是我做 hely 的出发点。让一个开餐馆的老板去学这种东西，就像让他去学写代码。未来的产品不该让人学提示词，应该是人说人话，机器去翻译。

### P5 从 7 步到 3 步 · 1.5 分钟
- **屏幕上：** 上面一排 7 个灰格（找参考图 → 学提示词 → 写英文 → 调参数 → 抽卡 → 修图 → 导出），点一下收缩成 3 个亮格：**选 → 填 → 生成**。
- **讲稿：** hely 的核心路径只有三步：选一个喜欢的案例，填自己的店名和菜品，点生成。提示词还在，只是藏到了后面，用户看不见。
- ⚠️ "7 步"是我按常见流程排的示意，不是统计数字。讲的时候说"大概要七八步"即可。你觉得不准可以改。

### P6 双层模板：一份给人，一份给 Agent · 1.5 分钟
- **屏幕上：** 同一个案例卡片，翻过来两面：正面是给人看的表单（店名、菜品、上传图），背面是给 Agent 看的 agent_schema（结构化字段）。下方一条小时间线：GUI → Agent 工作流 → Agent-first。
- **素材：** 仓库里《Agent产品形态的哲思》、docs/project-overview.md
- **讲稿：** 开工第一天我写的不是代码，是一篇《Agent 产品形态的哲思》。我的判断是：今天是人点按钮，明天是 Agent 替人干活，后天产品直接给 Agent 调用。所以 hely 的每个模板都存两份：人看表单，Agent 看结构。这是我做过最"有远见"的决定——但后面你会看到，远见不等于有人用。

- **讲稿：** 快速过，挑三个点讲：第一天就上线了原型；第四天接上了登录和数据库；7 月最拼，一个月提交 133 次。然后指着 9 月那根几乎看不见的柱子："这里先留个悬念，第 04 章讲。"

### P8 现场互动「数一数」：做一个网站要几种角色？ · 2.5 分钟
- **屏幕上：** 一个空的"团队"格子，讲师每点一下翻出一张角色牌：产品经理、UI 设计、前端、后端、数据库、运维部署、支付对接、域名备案、内容采集、测试、客服、运营推广……右上角计数器跟着跳。最后所有牌都盖上同一个头像：我 + AI。
- **互动：** 先请大家喊数字，再一张张翻。
- **讲稿：** 放在三年前，这至少是一个 8–10 人的团队。现在一个人加 AI 能做完——**除了最后两张**（运营推广、客服）。翻到最后两张时，牌是灰的："这两张我没做。"给 04 章埋伏笔。

### P9 Skill 当生产线 · 3 分钟
- **屏幕上：** 一条流水线：**采集 → 反译 → 封装 → 上架**，四个工位。每个工位下挂对应的 Skill 名字（8 个 hely-case-*：taxonomy / tags / form-schema / agent-schema / review-orchestrator / import-update / adaptation-strategy / user-guide）。人只站在一个位置：审美判断。右侧大数字：**1689 个案例**。
- **素材：** 提交 c0d4982（2026-06-08）
- **讲稿：** 我的做法是：找大量好图和提示词做成案例，再把"怎么把一张图变成模板"这件事本身做成 Skill，让 AI 按 Skill 批量干。我只做一件事：这张图好不好看、要不要上架。网站就是靠这些 Skill 一点点长起来的。这一页可以拍照——**把你重复做三次以上的事，写成 Skill。**

### P10 每个模型只管一块 · 2.5 分钟
- **屏幕上：** 一张分工表，每行可以点开看"为什么是它"。
  | 活 | 谁来干 | 为什么 |
  |---|---|---|
  | 听懂话、匹配案例、自动填表 | DeepSeek | 便宜、中文好 |
  | 画图、改图 | gpt-image-2 | 只有这一步必须用最贵的 |
  | 规划修改、检查结果 | 视觉模型 | 要看得懂图 |
  | 反推提示词 | GPT-4.1 | |
  | 抠图 | BiRefNet（本地） | 不花钱、保留原像素 |
  | 放大、改色 | 纯程序（sharp） | 根本不需要 AI |
- **讲稿：** 一句话：贵的模型只用在刀刃上。很多人一上来所有事都扔给最强的模型，又贵又慢。能用程序解决的，就不要用 AI。

### P11 攻破生图 API · 2 分钟
- **屏幕上：** ⚠️ 待你补充经过后再设计。
- ⚠️ 需要你讲一下：卡在哪、怎么解决的、花了多久。我建议做成"三个坑"的格式，每个坑一句话。

### P12 数字墙 · 1.5 分钟

## 03 / 翻车现场（8 分钟）

### P13 10 月 28 日：存储和登录一起挂了 · 3 分钟
- **屏幕上：** 一张"事故卡"：时间、症状、原因、怎么修、多久恢复。
  - 症状：用户登录不了，图片也打不开
  - 原因：Supabase 免费额度超了（402），登录和存储都放在它上面，一起挂
  - 修法：存储迁到 Cloudflare R2
  - 恢复：约一周
- **素材：** docs/incidents/2026-10-2x～10-31；⚠️ 当时的报错截图（你在之前的对话里给过，需要重新提供）
- **讲稿：** 教训两条：第一，免费额度是定时炸弹，用量起来那天就是它炸的那天；第二，鸡蛋不要放在一个篮子里。顺便说一句：这一周里有没有用户来问？——我也不知道，因为我没有和用户的联系渠道。（呼应 04）

### P14 现场互动「找错」：一个正常订单为什么失败？ · 3 分钟
- **屏幕上：** 上方是一个真实订单："把图二的辣椒鱼头放进图一"，结果报错"系统未完成编辑计划解析"。下方是这个请求经过的一排"关卡"，每道关卡都写着它当初为什么被加上（因为哪次事故）。请大家点：哪一道出了问题？
- **互动：** 让大家猜，点任何一道都显示"这一道本身没错"。最后揭晓：**每一道都没错，加在一起就错了。**
- **素材：** ⚠️ 11/16 的报错截图（需要重新提供）；关卡列表我从仓库文档里整理
- **讲稿：** 每出一次事故，我就加一道检查，想让系统更安全。加到后来，一个普通的"把鱼头放进图里"都过不去了。11 月 4 日加的原图限额、11 月 7 日加的全量规划，就是功能变复杂的根源。

### P15 定下的原则：失败要比交付难 · 2 分钟
- **屏幕上：** 三张原则卡，依次点亮：
  1. **失败要比交付难**——系统要拒绝一个订单，得有比"交出去"更硬的理由
  2. **不退单，照常扣费**——不再用退单来掩盖问题
  3. **带图创作改回直出**——像 GPT 那样直接出图，删掉中间的关卡
- **讲稿：** 11 月 17 日，我把带图创作改回了最简单的样子。这件事让我想明白：系统的复杂度，往往是对过去事故的过度反应。

### P17 真实数据 · 2 分钟
- **屏幕上：** 三个大数字：注册人数 / 生成次数 / 付费人数。⚠️ 等你提供后台截图。
- **讲稿：** 把数字亮出来，不解释，停三秒。然后说："377 次提交，换来这些用户。不是 AI 不行，是我把力气都花在了我舒服的地方。"

### P18 唯一一次真实需求：五连图 · 2.5 分钟
- **屏幕上：** 左边：10 月 7 日收到的一段 32 秒视频截图（商家怎么做大众点评/抖音的五联图）。右边：五连图从 v1 到 v7 的演变，10/23 改成让模型设计整张图。底部一行字：**半年里，唯一一次由真实用户的痛点推动的大更新。**
- **素材：** docs/local-dining-creative-plan-2026-10-07.md；五连图成品截图（我来截）
- **讲稿：** 其他所有功能，都是我觉得用户会需要。只有五连图，是一个人告诉我：本地商家每次上新都要做五张连着的图，很痛苦。这个功能做得最快、改得最多、也最像一个产品。——如果我一开始就这样做每一个功能呢？
- ⚠️ 提醒你的那个人，能不能讲是谁（比如"一个做本地生活的朋友"）？

### P19 builder 的舒适区 · 2.5 分钟
- **屏幕上：** 左右两栏对比：
  - 写代码：改一行，一秒就看到结果；今天能做完；做完就有成就感
  - 做推广：发了没人看；不知道哪里错了；一个月都没反馈
  - 下方一行：**代码 AI 能写，用户 AI 不会帮你找。**
- **讲稿：** 为什么我一直 build？因为 build 有即时反馈，推广没有。人天然会往有反馈的地方跑。AI 让 build 变得更快、更爽，反而让我更容易躲在里面。⚠️ 这里可以接上 9 月只有 1 次提交的原因（等你补）。
